# 通用 AI Coding 规则路由说明

本目录是部门通用 AI Coding 基础规范包中的规则入口。AI 助手或项目成员在使用本规范时，不应一次性读取全部规则文件，而应根据当前任务场景按需查阅对应文档。

本目录的目标不是堆积规则，而是为项目提供一套可初始化、可扩展、可留痕的共性工作机制。

## 1. 使用原则

### 1.1 先看入口，再读细则

进入一个项目或开始一项需求前，应先通过本文件确认当前任务需要查阅哪些规则，再按需读取对应文档。

### 1.2 禁止一次性全文加载

除非项目规模很小或用户明确要求，否则不应在单次会话中一次性读取本目录下所有规则文件。应优先保护上下文空间，保证 AI 在当前任务上保持聚焦。

### 1.3 通用规则不能替代项目专属规则

本目录中的规则用于定义跨项目通用的方法和底线，不直接表达某个具体项目的架构、模块、技术细节和专项约束。进入具体项目后，仍应读取该项目初始化生成的项目专属规则。

### 1.4 路径锚定优先于规则包位置

`.design-rules/` 是规则包位置，不是需求工作区位置。  
后续需求工作区 `.design/` 的归属只看**逻辑项目根目录**，不看 `.design-rules/` 当前位于哪个子目录。

逻辑项目根目录按仓库形态确定：

- **单仓项目**：代码仓库根目录就是逻辑项目根目录，`.design-rules/`、`.design/` 与代码由同一仓库管理
- **多仓项目**：承载多个独立代码仓库的壳目录就是逻辑项目根目录；壳目录自身作为治理仓库，统一管理 `.design-rules/`、`.design/` 和项目级文档
- 多仓项目中的各代码仓库继续独立管理分支、提交和远程同步；治理仓库不得追踪子仓库内容，应通过精确的 `.gitignore` 目录规则排除

这意味着：

- 即使 `.design-rules/` 位于 `docs/`、`docs/develop/` 或其他文档目录下，`.design/` 仍应创建在逻辑项目根目录
- 不得因为规则包位于某个文档目录中，就把 `.design/` 误创建到该文档目录下
- 如果当前会话无法确认仓库形态或逻辑项目根目录，应先完成确认，再创建工作区

## 2. 规则文件索引

### `README.md`

规则路由入口。用于说明整个基础规范包的用途、使用原则和文件分工。

### `bootstrap-protocol.md`

会话接力与阶段门禁规范。用于指导 AI 在新会话中如何恢复工作区状态、如何根据阶段控制可执行动作。

适合在以下场景查阅：

- 新会话开始时
- 接手已有 `.design` 工作区时
- 需要判断当前阶段是否应进入代码实现时

### `workspace-spec.md`

需求工作区规范。用于定义 `.design/<需求工作区>/` 的目录结构、默认文件清单、阶段职责和最小留痕要求。

适合在以下场景查阅：

- 准备为需求创建工作区时
- 需要确认工作区默认应生成哪些文件时
- 需要判断设计、计划、执行记录应写入哪里时
- 需要确认工作区最小必备内容时

### `project-init-spec.md`

项目初始化规范。用于指导项目如何接入通用基础包、如何生成项目专属规则，以及如何维护这些规则。

适合在以下场景查阅：

- 老项目第一次接入部门 AI Coding 体系时
- 新项目在研发启动阶段建立第一版规则时
- 需要确认项目专属规则最小产物时

### `programming-spec.md`

通用编程底线规范。用于定义跨项目适用的分层边界、异常暴露、可观测性和 AI 不得擅自脑补业务规则等基础要求。

适合在以下场景查阅：

- AI 准备编写或修改代码时
- 需要判断某种实现方式是否违反通用工程底线时
- 需要区分“部门通用底线”和“项目专项约束”时

## 3. 触发矩阵

| 当前场景 | 优先读取 |
| :--- | :--- |
| 项目首次接入 | `project-init-spec.md`，先识别单仓或多仓形态 |
| 老项目初始化 | `project-init-spec.md` + 项目初始化后生成的项目专属规则 |
| 新项目初始化 | `project-init-spec.md` + 项目目标/架构草案 |
| 新需求开始前 | `workspace-spec.md` + 项目专属规则 + 先检查逻辑项目根目录下是否已有 `.design/` |
| 接手已有工作区 | `bootstrap-protocol.md` + 当前工作区内容 |
| 进入代码实现 | `programming-spec.md` + 项目编码补充约束 |
| 判断某规则该不该长期沉淀 | `project-init-spec.md` + `project-rules/README.md` |
## 4. 推荐使用顺序

### 场景一：项目首次接入

推荐读取顺序：

1. `README.md`
2. `project-init-spec.md`
3. 项目初始化后生成的项目专属规则

### 场景二：需求开始前创建工作区

推荐读取顺序：

1. `README.md`
2. `workspace-spec.md`
3. 项目专属规则中与当前需求相关的架构、模块或专项约束

### 场景三：接手已有工作区继续推进

推荐读取顺序：

1. `README.md`
2. `bootstrap-protocol.md`
3. 当前需求工作区中的计划、执行和约束内容

### 场景四：进入代码实现

推荐读取顺序：

1. `README.md`
2. `programming-spec.md`
3. 当前项目的编码补充约束和专项规则

## 5. 与项目专属规则的关系

部门通用基础规则负责回答以下问题：

- AI Coding 采用什么总体工作机制
- 项目应如何建立规则入口
- 需求应如何通过工作区推进
- 代码实现应遵守哪些通用底线

项目专属规则负责回答以下问题：

- 当前项目的架构和技术栈是什么
- 当前项目的模块边界和目录组织是什么
- 当前项目有哪些特殊约束和复用要求
- 某类需求在当前项目中应该优先参考哪些模块和规则

两者关系可以概括为：

- 通用基础规则提供方法框架
- 项目专属规则提供真实上下文

## 6. 常见反模式

以下用法不符合本基础包设计初衷：

- 只复制 `.design-rules` 到项目中，但不执行项目初始化
- 把 `.design-rules/` 所在目录误当成 `.design/` 工作区归属目录
- 建立了 `.design` 工作区，但不持续维护 `04-plan` 和 `05-execution`
- 所有项目不分类型机械套用全部模板
- 项目专属规则只初始化一次，后续长期不更新
- 进入实现前不看项目专属规则，只看通用基础规则
- 把通用基础规则当成某个项目的具体实现指南

## 7. 维护原则

本目录中的规则应保持稳定、简洁、跨项目可复用。以下内容不应直接写入本目录主线规则：

- 某个具体项目的实现细节
- 强绑定某一技术栈的微观实践
- 高度依赖某个业务领域的特殊约束
- 仅适用于某一类项目的专项说明

如确有需要，应在项目专属规则或专项扩展规范中补充，而不是污染通用基础包主线。
