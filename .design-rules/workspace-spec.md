# 需求工作区规范

本规范用于定义项目中 `.design/<需求工作区>/` 的工作方式。工作区是需求分析、方案设计、任务拆解、执行记录和过程留痕的统一载体。

本规范强调结构化推进和最小可审计留痕，不要求所有需求都写成厚文档，但要求每个需求都能通过工作区形成可回溯记录。

## 1. 基本要求

### 1.1 每个需求必须有独立工作区

每个进入开发流程的需求，都应在逻辑项目根目录下的 `.design/` 中建立对应工作区，用于承载该需求的全过程记录。

### 1.1.1 逻辑项目根目录

- 单仓项目以代码仓库根目录作为逻辑项目根目录
- 多仓项目以承载各独立代码仓库的壳目录作为逻辑项目根目录；壳目录自身作为治理仓库
- 多仓项目的 `.design-rules/` 和 `.design/` 均位于壳目录，各子仓库仍保持独立 Git 管理

### 1.1.2 路径锚定规则

`.design/` **必须创建在逻辑项目根目录**，这是硬约束。

禁止出现以下错误放置方式：

- 创建在 `.design-rules/` 所在目录下
- 创建在 `docs/`、`docs/develop/` 或其他文档目录下
- 创建在某个模块子目录下，却将其当作项目级需求工作区

如果当前会话中仓库形态或逻辑项目根目录不明确，应先完成确认，再创建 `.design/<需求工作区>/`。

### 1.1.3 首次创建与后续复用规则

`.design/` 是**项目级固定目录**，不是每个需求都要重新创建的目录。

正确方式如下：

- **首次使用**：如果逻辑项目根目录下还没有 `.design/`，先创建 `.design/`，再在其下创建当前需求的工作区目录
- **后续使用**：如果逻辑项目根目录下已经存在 `.design/`，应直接复用该目录，并在其下继续创建新的需求工作区目录

这意味着：

- 不应因为来了一个新需求，就重复创建新的 `.design/`
- 后续需求真正新增的是 `.design/<需求工作区>/`
- 如果 `.design/` 已存在，应优先查找并复用，而不是重新选择其他位置创建

### 1.2 工作区必须进入版本库并关联代码提交

工作区不是个人草稿，也不是会后纪要。凡需求进入开发并产生代码变更，工作区内容必须进入版本库，并与对应代码提交形成可追溯关联。

- 单仓项目：工作区与代码由同一仓库管理，原则上随对应代码一起提交
- 多仓项目：工作区由壳目录治理仓库管理，各子仓库独立提交和推送；工作区应记录涉及仓库、分支、Commit ID 以及 MR/PR（如有）
- 多仓项目建议先完成各子仓库的代码提交与推送，再回填工作区中的关联信息，最后提交治理仓库
- 建议在代码提交正文或 MR/PR 描述中反向引用 `.design/<需求工作区>/`，形成双向追溯
- 多仓修改存在依赖顺序时，应按 `04-plan` 约定执行；部分仓库提交或推送失败时，应记录各仓库真实状态，不得将需求标记为已完成
- 发生 rebase、squash 或补充提交后，应在需求收口前回填最终有效的 Commit ID
- 不要求治理仓库和子仓库使用相同分支名、提交次数或 Git 历史

### 1.3 工作区是执行载体，不是静态归档区

工作区应随着需求推进持续更新。只创建目录或只保留初始模板而不维护，视为未真正使用工作区机制。

## 2. 强制级别说明

### 2.1 必须

- 建立独立需求工作区
- 工作区进入版本库，并与代码提交形成可追溯关联
- 维护 `04-plan`
- 维护 `05-execution`

### 2.2 条件必须

- 当需求存在明显技术风险、兼容性风险、性能风险或方案不确定性时，必须使用 `02-research`
- 当需求跨多个主题或设计明显复杂时，必须拆分 `03-design`
- 当当前需求存在特殊边界或依赖约束时，必须补充 `00-context`

### 2.3 推荐

- 在需求开始前优先建立工作区，而不是事后补写
- 在关键阶段完成后及时更新计划与执行记录
- 尽量让工作区内容与实现进度保持同步，而不是完工后一次性补齐

## 3. 标准目录结构

建议每个需求工作区采用如下结构：

- `00-context`
- `01-requirements`
- `02-research`
- `03-design`
- `04-plan`
- `05-execution`

该结构用于表达需求从上下文确认到执行落地的完整路径。

## 4. 默认文件清单

工作区文件按需求复杂度分为三类：最小必备版、条件生成、复杂需求增强拆分。

默认文件清单用于提供稳定命名参考，不要求所有需求都生成所有文件。普通需求应优先满足最小必备版；存在风险、接口、数据、验收或多轮变更诉求时，再按条件生成补充文件；复杂需求再按主题拆分。

### 4.1 最小必备版

适用于普通需求、低风险改动、单模块改动和需要快速形成可审计留痕的需求。

```text
.design/<需求工作区>/
├─ 00-context/
│  └─ handoff.md
├─ 01-requirements/
│  └─ requirements.md
├─ 03-design/
│  └─ design.md
├─ 04-plan/
│  └─ tasks.md
└─ 05-execution/
   └─ progress.md
```

| 文件 | 内容说明 |
| :--- | :--- |
| `00-context/handoff.md` | 记录当前阶段、接手必读、关键约束和下一步动作，方便后续会话或其他成员快速接手。 |
| `01-requirements/requirements.md` | 记录原始需求、澄清结果、范围边界、不做范围和待确认问题。 |
| `03-design/design.md` | 记录主设计方案、关键变更点、影响模块和重要设计取舍。 |
| `04-plan/tasks.md` | 记录任务拆解、执行顺序、任务状态和下一步计划。 |
| `05-execution/progress.md` | 记录执行进展、已完成事项、涉及代码范围、阻塞和接手建议。 |

### 4.2 条件生成

适用于存在架构边界、接口变化、数据变化、技术风险、验收要求或多轮变更记录的需求。

```text
.design/<需求工作区>/
├─ 00-context/
│  ├─ architecture.md
│  └─ constraints.md
├─ 01-requirements/
│  └─ impact-checklist.md
├─ 02-research/
│  └─ validation.md
├─ 03-design/
│  ├─ API设计.md
│  └─ 数据模型设计.md
├─ 04-plan/
│  └─ acceptance.md
└─ 05-execution/
   └─ changelog.md
```

| 文件 | 内容说明 |
| :--- | :--- |
| `00-context/architecture.md` | 记录当前需求相关的架构上下文、模块关系和跨层边界。 |
| `00-context/constraints.md` | 记录当前需求必须遵守的约束、禁止事项、复用要求和风险边界。 |
| `01-requirements/impact-checklist.md` | 记录需求可能影响的模块、接口、数据、权限、发布和外部系统。 |
| `02-research/validation.md` | 记录技术验证、风险排除、可行性判断和对设计决策的影响。 |
| `03-design/API设计.md` | 记录接口新增、接口修改、请求响应、兼容策略和前后端契约。 |
| `03-design/数据模型设计.md` | 记录表结构、字段、数据流、数据迁移、兼容策略和数据归属。 |
| `04-plan/acceptance.md` | 记录验收标准、测试关注点、通过条件和不通过边界。 |
| `05-execution/changelog.md` | 记录多轮实现过程中的关键变更、调整原因和影响范围。 |

### 4.3 复杂需求增强拆分

适用于跨模块需求、跨系统需求、长期演进需求、架构治理需求、Agent/Skill/报表/权限等复杂需求。

复杂需求可在最小必备版和条件生成文件的基础上继续拆分。

| 文件或目录 | 内容说明 |
| :--- | :--- |
| `01-requirements/raw.md` | 记录未经加工的原始需求、口头输入、截图说明或外部需求文本。 |
| `01-requirements/clarified.md` | 记录澄清后的需求主版本，包括已确认范围和暂不纳入范围。 |
| `01-requirements/open-questions.md` | 记录仍需业务、产品、技术负责人确认的问题。 |
| `01-requirements/clarified-<专项主题>.md` | 记录某个专项方向的澄清结果，例如权限、数据、Agent 或外部系统。 |
| `02-research/01-<研究主题>.md` | 记录专项研究主题，例如历史代码盘点、性能验证或兼容性分析。 |
| `03-design/01-<专题设计>.md` | 记录专题设计，例如页面交互、权限模型、执行链路或核心流程。 |
| `03-design/README.md` | 记录设计目录索引、各设计文件职责和推荐阅读顺序。 |
| `03-design/<专项子目录>/README.md` | 记录专项子目录的设计入口和内部文件说明。 |
| `03-design/<专项子目录>/A-<设想方案>.md` | 记录备选方案、设想方案或暂不落地但需要保留的设计探索。 |
| `03-design/<专项资料目录>/00-索引.md` | 记录大量专项资料、环境变量、配置项或设计资产的索引。 |
| `04-plan/optimization-backlog.md` | 记录本期不强制完成但后续值得优化的事项。 |
| `06-testing/01-测试用例清单.md` | 记录测试场景、测试用例、边界条件和验收覆盖点。 |
| `06-testing/02-测试执行记录.md` | 记录实际测试结果、发现问题、修复情况和最终结论。 |

注意：`requirements.md` 与 `raw.md`、`clarified.md`、`open-questions.md` 不建议同时作为强制项。普通需求可用 `requirements.md` 聚合，复杂需求再拆分。

## 5. 各阶段职责

### 5.1 `00-context`

用于记录当前需求必须依赖的上下文和边界信息，例如：

- 当前需求涉及的系统边界
- 当前需求相关的技术或业务约束
- 当前需求依赖的已有模块、已有规则或已有流程

如果项目已有较完整的项目专属规则，本目录可以适度简化为引用或补充，而不要求重复抄写大量项目背景。

最小产出要求：

- 当前需求依赖的关键边界
- 当前需求必须遵守的特殊约束或已有规则引用

推荐补充文件：

- `00-context/handoff.md`

该文件用于作为需求级“最小接手契约页”，帮助其他同事或后续会话快速接手当前工作区。

建议至少包含：

- 当前所处阶段
- 是否允许直接进入代码修改
- 接手必读文件
- 当前轮次主要目标
- 当前需求特有约束
- 修改代码后必须同步更新的工作区文件

推荐模板：

```markdown
# 接手说明 - <需求名>

## 1. 当前阶段
- 当前所处阶段：
- 是否允许直接进入代码修改：是 / 否

## 2. 接手必读
- 必读文件 1：
- 必读文件 2：
- 必读文件 3：

## 3. 当前目标
- 当前这一轮最主要的任务是：
- 当前不应扩展处理的内容是：

## 4. 关键约束
- 本需求特有的边界：
- 本需求特有的禁止事项：
- 需要优先复用的模块 / 能力：

## 5. 当前状态摘要
- 上一轮已完成：
- 当前进行中：
- 当前阻塞点：

## 6. 收尾要求
- 修改代码后必须同步更新：
  - `04-plan/...`
  - `05-execution/...`
- 未完成状态回写前，不得视为本轮完成
```

### 5.2 `01-requirements`

用于记录需求澄清过程，包括但不限于：

- 原始需求
- 澄清后的功能边界
- 已确认范围与暂不纳入范围
- 待确认问题
- 影响面分析

这是需求从模糊描述进入可设计状态的关键区域。

最小产出要求：

- 原始需求
- 已确认范围
- 暂不纳入范围或待确认问题

跨模块或多仓需求建议在 `impact-checklist.md` 中使用以下结构：

| 所属仓库 | 模块 / 目录 | 影响类型 | 影响说明 | 处理状态 |
| :--- | :--- | :--- | :--- | :--- |
| `<仓库名>` | `<相对路径或模块>` | 新增 / 修改 / 删除 / 配置 |  | 待确认 / 待处理 / 已完成 |

### 5.3 `02-research`

用于记录高风险验证或前置探索结果，例如：

- 技术可行性验证
- 边界行为验证
- 原型试验结论
- 关键不确定性排除结果

并非所有需求都需要完整使用该目录，但当需求存在明显技术风险、性能风险、兼容性风险或方案不确定性时，应保留此部分记录。

最小产出要求：

- 核心风险点
- 验证结论
- 是否影响后续设计决策

### 5.4 `03-design`

用于记录系统设计结果，包括但不限于：

- 方案说明
- 关键流程
- 模块分工
- 数据与接口变化
- 重要设计取舍

当设计内容较复杂时，应按主题拆分文档，避免长期把所有内容堆叠在单一文件中。

最小产出要求：

- 方案结论
- 关键变更点
- 重要边界或取舍

### 5.5 `04-plan`

用于将设计结果转化为可执行任务。该目录是需求执行阶段的核心区域之一，应至少覆盖：

- 任务拆解
- 执行顺序
- 核心验收点
- 当前任务状态

没有任务拆解的设计，很难稳定进入执行阶段。

最小产出要求：

- 任务拆解
- 实施顺序
- 当前状态或待确认点

### 5.6 `05-execution`

用于记录执行过程和结果。该目录是需求执行阶段的另一核心区域，应至少覆盖：

- 编码进展
- 关键决策
- 重要变更说明
- 当前阻塞或遗留问题

该区域用于保证后续会话接力和事后回溯可用。

最小产出要求：

- 当前进展
- 已完成事项
- 重要阻塞或决策变化

固定收尾要求：

- 如果本轮已经修改代码，则结束前必须同步更新 `04-plan` 的当前任务状态
- 如果本轮已经修改代码，则结束前必须在 `05-execution` 中追加本轮进展
- 如果本轮出现重要决策变化、阻塞或实现偏差，则必须在 `05-execution` 中明确记录
- 若代码已修改但上述状态未同步更新，则本轮任务不得视为完成

推荐模板：

```markdown
# 执行进展 - <需求名>

> [!IMPORTANT]
> 本轮如果已修改代码，则结束前必须完成以下动作：
> 1. 更新 `04-plan` 中当前任务状态
> 2. 在本文件追加本轮进展
> 3. 记录关键决策、阻塞或偏差
> 4. 未完成以上动作，不得视为本轮完成

## 本轮记录
- 本轮完成：
- 本轮涉及仓库及代码范围：
- 本轮关键决策 / 偏差：
- 当前阻塞：
- 下一轮接手建议：

## 代码提交关联

| 仓库 | 相对路径 | 分支 | Commit ID | MR / PR | 推送状态 |
| :--- | :--- | :--- | :--- | :--- | :--- |
|  |  |  |  |  | 未提交 / 已提交未推送 / 已推送 |
```

## 6. 轻量例外场景

以下场景允许适度轻量化，但不允许完全绕过留痕：

- 极小范围、低风险的单点修复
- 紧急线上修复
- 验证性小改动或短期试验

在这些场景下，至少仍应保留：

- 需求主题
- 最小设计或处理说明
- 执行记录
- 已进入版本库且能够关联代码提交的留痕

## 7. 命名与组织建议

### 7.1 工作区命名

工作区名称应清晰表达需求主题，便于团队理解和后续回溯。

推荐使用中文或团队内部统一的高可读命名方式，不建议使用难以理解的临时缩写或纯技术性代号。

### 7.2 设计文档组织

当 `03-design` 内容较多时，应按稳定主题拆分文档，并保留一个主入口或索引文档，说明各文档职责与阅读顺序。

### 7.3 执行记录组织

`05-execution` 中的内容应体现真实推进过程。建议至少保留进度记录和关键决策记录，避免只在需求结束后一次性补写结果。

## 8. 推荐使用方式

### 8.1 新需求开始时

建议先建立工作区，再进入需求澄清和方案设计，而不是先写代码后补文档。

### 8.2 需求推进过程中

建议在以下时点更新工作区：

- 需求边界被确认后
- 设计方案形成后
- 计划被拆解后
- 开发完成一个关键阶段后
- 出现重要决策变化或阻塞后

### 8.3 需求结束前

在结束需求或提交治理仓库前，应确认：

- 工作区内容已同步更新
- 计划与执行记录能对应当前实现
- 代码变更与工作区主题一致
- 多仓项目涉及的各子仓库、分支、Commit ID、MR/PR（如有）和推送状态已经记录
- 代码提交正文或 MR/PR 描述能够反向定位需求工作区；发生 rebase 或 squash 时，工作区记录已更新为最终有效 Commit ID

如果本轮已修改代码，还应确认：

- `04-plan` 中当前任务状态已同步
- `05-execution` 中本轮进展已追加
- 接手他人时下一轮所需的最小上下文已经留下

推荐在 `04-plan` 或等效任务文件中保留结构化状态字段：

- 当前任务：
- 状态：未开始 / 进行中 / 已完成 / 阻塞
- 下一步：

## 9. 审计关系

工作区是部门 AI Coding 第一阶段审计的核心载体。只要需求已经进入开发，审计将重点检查：

- 是否存在对应工作区
- 是否有基本过程记录
- 是否已进入版本库
- 是否能够追溯到对应仓库、分支和代码提交
