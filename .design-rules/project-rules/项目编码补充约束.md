# 项目编码补充约束

## 1. 适用说明

本文件补充 **CyberStrikeAI 内部二次开发** 相对于部门通用 `programming-spec.md` 的专项约束。通用底线（分层、禁止脑补业务、禁止静默降级、提交信息格式等）仍以 `.design-rules/programming-spec.md` 为准。

本文档从现有 `docs/zh-CN/contributing-guide.md`、`docs/zh-CN/developer-guide.md` 与代码实践提炼，**不替代**上述文档的细节 Checklist。

## 2. 协作与版本管理

### 2.1 分支与远程

| 规则 | 内容 |
| :--- | :--- |
| 日常开发分支 | `开发分支`（当前活跃线；若重命名以仓库为准） |
| 禁止误用 | 不在 `main` 上堆叠日常功能；`main` 用于合并 `upstream` 后验证 |
| 推送目标 | 代码变更同步提交 **`origin` 与 `gitlab`**，保持**同名分支** |
| 上游合并 | 从 `upstream`（`Ed1s0nZ/CyberStrikeAI`）合并到 `main` 验证通过后，再并入开发分支 |

### 2.2 提交信息

遵循 `programming-spec.md` 第 6.5 节：`<类型>(<范围>): <简短中文描述>`，类型为 `feat|fix|docs|...`，描述简体中文、≤50 字。

一次提交只覆盖一个可独立说明、验证和回退的变更；**不得混入** `.design/` 工作区（启用后）、无关格式化或其他需求改动，除非该需求明确要求。

### 2.3 与上游的关系

- 内部需求以 `origin`/`gitlab` 开发线为准，**不假设**每个改动都需要贡献回 `upstream`
- 合并 `upstream` 时优先保留双方意图，冲突区域需人工确认，禁止 AI 无确认整库覆盖

## 3. 新增业务能力（完整配方）

新增业务模块时，`developer-guide.md` 要求至少考虑以下 10 项，**缺一项易返工**：

1. 数据模型（SQLite 表与迁移）
2. Handler（参数、错误码、分页）
3. Audit（管理写操作）
4. Monitor（长任务状态）
5. MCP（是否暴露给 Agent）
6. HITL（工具审批边界）
7. OpenAPI（`internal/handler/openapi.go`）
8. Frontend（i18n、loading/empty/error）
9. Tests（database、handler、边界）
10. Docs（`docs/zh-CN/` 与 `docs/en-US/` 成对）

## 4. API 与错误响应

- 错误响应保持：`{ "error": "machine_readable_code", "message": "给用户看的说明" }`
- 修改类接口写审计；长任务写监控或任务状态
- 接口默认受认证保护，平台回调除外
- 新增公开 API 必须更新 OpenAPI 与相关 Recipe/文档

## 5. 配置变更

- `internal/config/config.go` 增加字段
- `config.example.yaml` 带注释示例
- 省略字段有**安全默认值**；旧 `config.yaml` 必须能启动
- 说明是否支持 Web 设置页**热应用**（`handler/config.go`）
- 影响高风险能力时更新安全文档

## 6. 工具与 Agent 扩展

| 扩展方式 | 优先路径 | 约束 |
| :--- | :--- | :--- |
| 命令类工具 | `tools/*.yaml` | 见 `tools/README.md`；`short_description` 可被 tool_search 检索 |
| 角色 | `roles/*.yaml` | **最小工具集**，勿默认全工具 |
| 子 Agent | `agents/*.md` | front matter + 系统提示词 |
| Skill | `skills/<name>/SKILL.md` | 见 skills 指南 |
| Go 内置 MCP 工具 | `internal/app/*_tools.go` | 明确 InputSchema、超时、HITL |

高风险工具（Shell、写文件、C2、WebShell、批量扫描等）**不得**默认加入全局 HITL 白名单；须回答：谁能调用、是否 HITL、审计内容、取消/禁用方式（见 `contributing-guide.md`）。

## 7. 前端变更

- 复用 `apiFetch`、modal、通知、现有样式
- 所有**新增可见文案**同步 `web/static/i18n/zh-CN.json` 与 `en-US.json`（渐进迁移中的页面亦适用新改动）
- 删除与高风险操作需确认框；控制台无报错
- **禁止**将 API Key 等敏感信息写入前端

i18n 规范见 `docs/zh-CN/frontend-i18n.md`。

## 8. 数据库变更

- 迁移写在 `internal/database/` 初始化或模块迁移函数，**幂等**
- 必须兼容已有 `data/conversations.db`（及 knowledge 库）
- 新字段合理默认值；大表索引谨慎
- 单测覆盖空库与旧库升级路径
- 发布说明提醒备份 `data/`

详见 `数据库与数据约束.md`。

## 9. 测试优先级

改动后至少运行**受影响包**的 `go test`；全量回归：`go test ./internal/...`。

优先补测区域（高故障率）：

- 配置热应用
- HITL 审批分支
- Shell 超时与无输出
- 外部 MCP 失败恢复
- 知识库索引与检索
- WebShell 编码
- SQLite 迁移兼容

## 10. 文档

重要功能需补：用途、配置、操作流程、风险边界、排错、源码锚点。中英文文件名对齐，更新 `docs/README.md` 及语言子目录导航。

提交文档前若存在 `scripts/check-docs.py`，应执行通过。

## 11. 禁区说明

| 区域 | 原因 | 修改前需确认 |
| :--- | :--- | :--- |
| `internal/security/` RBAC 核心 | 全平台访问控制 | 需求、安全负责人 |
| 全局 HITL 白名单与审批模式 | 影响所有工具 | 配置变更评审 |
| C2/WebShell 默认启用策略 | 法律与授权风险 | 部署环境与授权范围 |
| `internal/database/` 破坏性迁移 | 数据不可恢复 | 备份与回滚方案 |
| 无需求的大规模格式化 / 重命名 | 干扰 review 与合并上游 | 禁止 |

## 12. AI 使用提示

- **最容易违反的规则**：只改 Handler 不更 OpenAPI/i18n；新工具未绑角色；迁移不幂等；向 `main` 直接提交
- **编码前优先检查**：`contributing-guide.md` 对应 Checklist、本需求是否触及高风险模块、是否在正确分支
- **冲突优先级**：用户明确指令 > 本文件与项目专属规则 > `programming-spec.md` > 通用惯例
