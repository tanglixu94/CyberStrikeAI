# 项目概览

## 1. 项目定位

- **项目名称**：CyberStrikeAI（Go 模块名：`cyberstrike-ai`）
- **项目类型**：单体 Go Web 服务 + 静态前端；AI 原生网络安全智能执行与编排平台
- **当前阶段**：基于上游开源项目（`upstream`）的**内部二次开发**持续演进
- **主要服务对象**：内部安全团队；在获得明确授权的前提下开展渗透测试、漏洞验证、资产梳理等安全任务

项目将自然语言意图转化为受治理、可审计的安全行动，整合 Eino 智能体、MCP 工具、RAG 知识库、工作流、攻击链建模、资产管理、漏洞管理等能力。

## 2. 项目目标

- **项目解决的问题**：统一安全测试的规划、执行、人工监督、证据留存与复盘，降低多工具、多会话、多角色协作的碎片化成本
- **当前阶段的核心目标**：在内部仓库（`origin` / `gitlab`）的**开发分支**上持续交付内部需求；按需从 `upstream` 合并开源更新并验证后再并入开发线
- **本阶段不纳入范围的内容**：
  - 将本项目当作面向公众的独立开源产品运营（上游由 `upstream` 维护）
  - 在未明确授权的目标上执行扫描、利用或后渗透操作
  - 由 AI 在未确认需求时自行扩展业务规则或默认开启高风险能力（C2、WebShell、无审批 Shell 等）

## 3. 边界说明

- **本项目负责的范围**：
  - Web 控制台、API、Agent/MCP 编排、工作流、知识库、RBAC、审计与监控
  - `tools/`、`roles/`、`agents/`、`skills/` 等可配置扩展面
  - `plugins/`（Burp、浏览器扩展）与 `mcp-servers/` 作为可选集成，改动时需明确是否纳入当前需求
- **不属于本项目负责的范围**：
  - 上游开源社区的发版节奏与公开 Issue/PR 流程（内部以 `origin`/`gitlab` 为主）
  - 目标系统自身的业务逻辑与安全责任
  - 生产环境具体部署拓扑（**待后续在「发布与部署约束」中补充**）
- **与其他系统或团队的主要边界**：
  - **upstream**（`https://github.com/Ed1s0nZ/CyberStrikeAI.git`）：开源上游；`main` 分支保留用于合并上游，**日常开发不在 `main` 上进行**
  - **origin**（`https://github.com/tanglixu94/CyberStrikeAI.git`）：内部 fork，**默认 push 目标**
  - **gitlab**（`http://192.168.2.66:7077/gitlab/sapd/datagov/cyberstrikeai.git`）：内网镜像；与 `origin` **保持同名分支同步提交**

## 4. AI 使用提示

- **AI 在本项目中应优先关注的核心方向**：
  - 尊重现有分层（`handler` → `database` / `multiagent` / `mcp` 等），优先复用 `docs/zh-CN/` 与 `contributing-guide.md` 中的 Checklist
  - 改动涉及 Agent、工具、HITL、配置热应用、SQLite 迁移时，评估横向影响（见 `系统架构说明.md`）
  - 内部二次开发：提交同步 `origin` 与 `gitlab`，在**开发分支**工作，不直接向 `main` 堆叠日常功能
- **AI 不应擅自扩展的边界**：
  - 未在需求或文档中确认的业务规则、审批策略、默认工具白名单
  - 绕过 RBAC、HITL、审计的高风险操作
  - 将 `upstream` 合并冲突自行「整库重写」或大规模无关重构
- **后续需求推进应默认进入的工作机制**：`.design/<需求工作区>/`（**首条真实需求时再建立**；当前尚未启用）
