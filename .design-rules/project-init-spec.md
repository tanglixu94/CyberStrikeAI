# 项目初始化规范

本规范用于指导项目接入部门 AI Coding 体系时的初始化工作，定义项目何时初始化、初始化要产出什么、初始化完成后如何维护项目专属规则。

项目初始化的目标不是生成一批空文档，而是为项目建立可供 AI 和团队共同使用的规则入口和真实上下文。

## 1. 适用范围

本规范适用于以下两类项目：

- 存量项目：已经存在代码仓库并将持续开发的项目
- 增量项目：新立项、正在启动或尚未形成完整实现的新项目

## 2. 强制级别说明

### 2.1 必须

- 引入通用基础包
- 识别单仓或多仓形态，并明确逻辑项目根目录
- 形成项目专属规则最小集
- 明确后续需求通过 `.design` 工作区推进
- 明确项目专属规则责任人

### 2.2 条件必须

- 当项目存在明显 UI 规范边界时，补充 UI 类扩展规则
- 当项目存在明显数据、存储、报表或建模边界时，补充数据类扩展规则
- 当项目存在明显发布、部署或外部集成复杂度时，补充相应专项规则

### 2.3 推荐

- 在项目初始化完成后，选择一个真实需求验证工作机制
- 在首轮试点后回顾项目专属规则是否足够指导开发

## 3. 初始化目标

项目初始化的目标包括：

- 引入部门通用基础规范包
- 明确仓库形态、逻辑项目根目录和版本管理边界
- 生成项目专属规则第一版
- 建立项目后续使用 `.design` 工作区的前提条件
- 明确项目专属规则的责任人和维护方式

初始化的完成标准是“足以支撑后续需求在统一机制下开展”，不是“穷尽一切项目细节”。

## 4. 仓库形态与治理边界

初始化开始时必须先判断项目属于以下哪种形态：

- **单仓项目**：一个代码仓库承载完整项目，代码仓库根目录同时作为逻辑项目根目录和治理仓库
- **多仓项目**：同一项目由多个独立代码仓库组成，应在其共同上级建立壳目录；壳目录作为逻辑项目根目录和治理仓库

多仓项目应遵守以下边界：

- `.design-rules/`、`.design/` 和项目级文档统一放在壳目录下
- 各子仓库保留自己的 `.git/`、分支、提交历史和远程地址
- 壳目录通过精确的 `.gitignore` 规则排除各子仓库目录，不追踪或复制子仓库代码
- 项目专属规则应记录子仓库名称、相对路径、主要职责和远程地址
- 需求工作区负责记录跨仓影响及提交关联，不以合并 Git 历史替代跨仓追溯

## 5. 初始化分类

### 5.1 存量项目初始化

存量项目初始化以现有仓库和现有实现为基础，从真实代码、已有文档、目录结构、架构边界和团队约定中提炼项目专属规则。

### 5.2 增量项目初始化

增量项目初始化以项目目标和目标设计为基础，从业务范围、技术选型、目标架构、模块规划和协作方式中预生成项目专属规则，并在首轮开发后持续修正。

## 6. 项目专属规则产物模型

建议项目专属规则采用“5+X”模型。

### 6.1 最小必需 5 项

项目专属规则统一存放在逻辑项目根目录的 `.design-rules/project-rules/` 下。

所有项目初始化后，应至少产出以下文件：

1. `项目概览.md`
2. `技术栈与运行方式.md`
3. `系统架构说明.md`
4. `模块地图.md`
5. `项目编码补充约束.md`

### 6.2 按需扩展 X 项

根据项目类型和复杂度，按需补充专项规则，例如：

- `UI与交互约束.md`
- `数据库与数据约束.md`
- `发布与部署约束.md`
- `外部系统与接口约束.md`
- `专项开发约束.md`

扩展项的目标是表达当前项目的专项边界，不要求所有项目统一具备同样的扩展文档集合。

## 7. 存量项目初始化步骤

存量项目初始化建议按以下顺序进行：

1. 识别单仓或多仓形态，确认逻辑项目根目录
2. 多仓项目建立治理仓库、精确忽略子仓库目录，并登记子仓库清单
3. 引入通用基础包
4. 识别项目技术栈与运行方式
5. 识别系统分层与主要架构边界
6. 识别核心模块、高风险区域和复用优先模块
7. 整理当前项目特有的开发约束
8. 生成项目专属规则最小集
9. 使用一个真实需求验证 `.design` 工作机制和跨仓追溯方式

存量项目初始化应以“够用”为先，不应演变为全面历史考古。

## 8. 增量项目初始化步骤

增量项目初始化建议按以下顺序进行：

1. 识别单仓或多仓形态，确认逻辑项目根目录
2. 多仓项目建立治理仓库、精确忽略子仓库目录，并规划子仓库职责
3. 引入通用基础包
4. 明确项目目标与范围
5. 明确技术选型原则
6. 明确目标架构和模块划分
7. 明确目录结构与协作方式
8. 生成项目专属规则第一版
9. 建立首批 `.design` 工作机制
10. 在首轮开发后回填实现态规则

增量项目初始化应以“先立边界、再写代码”为原则，不应等到项目大量编码后再回头补做。

## 9. 初始化完成定义

项目初始化完成，至少应满足以下条件：

1. 已引入通用基础包
2. 已明确仓库形态和逻辑项目根目录
3. 多仓项目的治理仓库可正常使用，且不会追踪子仓库内容
4. 多仓项目的子仓库清单、职责和远程地址已经记录
5. 已形成项目专属规则最小集
6. 团队明确后续需求通过 `.design` 工作区推进
7. 至少有一条真实需求已验证工作区与代码提交可追溯关联
8. 各代码仓库仍可独立执行分支、提交、拉取和推送
9. 项目专属规则责任人明确

## 10. 项目专属规则更新触发器

出现以下情况时，项目专属规则应被视为需要更新：

- 架构分层或模块边界发生明显调整
- 新增核心模块、公共能力或关键目录
- 技术栈、运行方式或仓库组织方式发生变化
- 构建、发布、权限、数据或接口约束发生变化
- 团队在真实需求推进中沉淀出新的稳定开发规则

最小更新要求包括：

- 更新受影响的项目专属规则文件
- 明确新增或变更的边界
- 确保后续需求仍能据此正确进入 `.design` 工作区

## 11. 后续维护机制

项目专属规则是持续维护资产，不是一次性生成后永久有效的静态说明。

建议由项目技术经理或指定责任人发起更新，并在以下时机检查是否需要维护：

- 重要架构调整后
- 首轮试点需求结束后
- 迭代中出现 AI 明显误判项目边界后
- 团队发现已有规则无法支撑后续开发时

## 12. 与通用基础规则的关系

项目初始化规范用于连接“部门通用基础规则”和“项目专属规则”。

- 通用基础规则回答“工作机制是什么”
- 项目初始化回答“如何把这套机制接入当前项目”
- 项目专属规则回答“当前项目的真实上下文是什么”

只有三者形成闭环，AI Coding 规范才能真正进入项目日常开发。
