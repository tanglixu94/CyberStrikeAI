# 通用编程底线规范

本规范用于定义 AI 参与编码时需要遵守的跨项目通用工程底线。

本规范不试图替代具体项目的架构规范、技术规范或专项规则，也不负责规定某一种技术栈的最佳实践细节。凡涉及项目特有实现方式、框架微观用法、构建发布细节或专项领域约束，应由项目专属规则或专项扩展规范补充。

## 1. 适用范围

本规范适用于部门内纳入 AI Coding 规范体系的各类项目，包括但不限于前端项目、后端项目、平台项目、数据项目、集成型项目和 AI / Agent 类项目。

本规范在代码设计、代码修改、代码补全、问题修复和重构场景中均应被视为通用底线。

## 2. 使用原则

### 2.1 通用底线优先

当项目尚未明确项目专属规则时，AI 至少应遵守本规范中的通用底线，避免因无边界实现而引入明显工程风险。

### 2.2 项目规则优先于通用默认

当项目已存在明确的项目专属规则时，应在遵守本规范底线的前提下，以项目规则为准处理具体实现问题。

### 2.3 原则统一，细节因项目而异

本规范统一的是工程原则，而不是某个仓库的实现细节。不同项目可以在不违反本规范底线的前提下，自行采用适合自身的技术方案和代码组织方式。

## 3. 分层与职责边界

### 3.1 明确职责分层

AI 在编写或修改代码时，应尽量尊重当前项目已有的分层边界，避免将协议解析、业务逻辑、数据存取、外部集成、视图渲染等不同职责无序混写在同一层中。

### 3.2 不为赶进度绕过边界

如果项目中已经存在明确的模块、分层或公共能力，AI 不应为了追求局部快速实现而直接跨层访问、复制已有能力或绕过既有约束。

### 3.3 复用优先于重复发明

在当前项目已有稳定实现、已有公共模块或已有标准入口时，应优先复用，而不是在局部新增一套相似但不兼容的实现。

### 3.4 边界不清时先澄清

如果项目边界、模块职责或调用路径本身不清晰，AI 不应凭主观判断强行固化实现，应优先通过项目规则、工作区设计或人类确认来补足信息。

## 4. 业务逻辑约束

### 4.1 禁止擅自脑补业务规则

未经需求、规则文档或人类明确确认，AI 不得擅自引入业务判断规则、隐式状态机、推断逻辑或额外约束条件。

### 4.2 禁止无依据启发式推断

AI 不得自行发明启发式算法、模糊匹配规则、分类规则、评分规则、优先级规则或推断分支，除非这些逻辑已在需求、设计文档或项目规则中得到明确说明。

### 4.3 关键行为必须来源明确

对外可见的核心行为、关键分支、状态变化和数据处理规则，应能够追溯到需求说明、设计决策、项目规则或已有稳定实现，而不是来自 AI 的临场猜测。

### 4.4 边界条件应显式处理

AI 在实现业务逻辑时，应主动识别输入异常、空值、重复执行、状态冲突、权限边界、外部依赖失败等情况，并采用符合项目规则的方式进行显式处理，而不是默认忽略。

## 5. 异常处理与可观测性

### 5.1 禁止静默降级

未经明确设计和确认，不应擅自通过返回默认空值、吞掉异常、跳过关键步骤或悄悄改写输入等方式隐藏问题。

### 5.2 禁止空捕获和无反馈失败

不应编写空的异常捕获逻辑，也不应在关键失败发生后不给出任何错误信号。错误必须以合适方式暴露出来，以便定位和修复。

### 5.3 错误应可定位

当发生异常、失败或关键分支偏离时，相关代码应具备基本可定位性。日志、错误信息或执行记录应能够帮助研发人员回溯问题发生的上下文。

### 5.4 不得泄漏敏感信息

在日志、错误输出或调试信息中，不得直接暴露密码、密钥、凭证、隐私数据或其他敏感信息。必要时应采用脱敏、摘要化或安全替代方式表达。

## 6. 代码质量底线

### 6.1 代码应与当前项目风格保持一致

AI 编写的代码应尽量贴合当前项目已有的语言风格、结构习惯、命名方式和组织模式，避免在局部引入风格突变。

### 6.2 类型与结构应清晰

在支持类型系统的项目中，应尽量保证核心结构、函数输入输出、关键数据形态和边界对象具备清晰定义，避免依赖模糊结构维持短期可运行状态。

### 6.3 变更范围应可控

在解决具体问题时，应优先采用范围可控、意图明确的改动，而不是为一个局部问题引入无必要的大面积重构。

### 6.4 注释应解释边界与原因

需要补充注释时，注释应优先解释设计原因、边界条件、特殊约束和为何这样做，而不是简单复述代码表面行为。

### 6.5 Git 提交与变更管理

- 提交信息统一使用 `<类型>(<范围>): <简短中文描述>`；范围使用受影响的模块、页面或领域，无明确范围时可省略。
- 类型限定为：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`ci`、`revert`。
- 描述使用简体中文，以“添加”“修复”“优化”“重构”等动词开头；明确说明完成事项而非实现方式；不超过 50 个字符，末尾不加句号。必要的技术术语可保留英文。
- 一次提交只覆盖一个可独立说明、验证和回退的变更；不得混入无关文件、临时调试内容或其他需求的工作区改动。
- 提交前应确认暂存范围准确、不包含敏感信息，并同步更新需求工作区的计划、执行状态或交付说明。

> 本节约束项目的提交内容与提交信息；暂存、提交等 Git 操作的执行授权，仍以运行环境或上级规则为准。

## 7. 实现前检查清单

在进入实际代码修改前，建议至少检查以下问题：

- 当前需求边界是否已经明确
- 当前项目是否已有可复用实现
- 当前改动是否触及高风险模块或敏感链路
- 当前实现是否可能引入未确认的业务规则
- 当前项目是否有需要优先遵守的项目补充约束
- 当前需求工作区中的计划和设计是否足以支撑实现

如果以上问题中有多个无法回答，应优先回到项目专属规则或工作区，而不是直接进入编码。

## 8. 与项目专属规则的分工

本规范不负责定义以下内容：

- 某个具体项目的技术栈微观实践
- 某个具体项目的目录结构或模块地图
- 某个具体项目的构建、发布和部署路径
- 某个具体项目的 UI、数据库、接口或 Agent 专项约束

这些内容应由项目初始化后生成的项目专属规则或专项扩展规范补充。

## 9. 实施建议

在实际使用中，建议按以下顺序理解和应用本规范：

1. 先确认当前项目是否已有项目专属规则
2. 在项目规则基础上，以本规范作为通用底线校验
3. 在需求工作区中明确关键设计边界后，再进入实现
4. 在实现过程中持续检查是否出现了擅自脑补、绕过边界或静默降级等行为

## 10. 总结

本规范的核心目标不是提升代码“看起来多漂亮”，而是防止 AI 在缺乏边界、缺乏确认和缺乏约束的情况下做出工程上高风险的实现。

对部门 AI Coding 而言，最需要统一的不是某个框架技巧，而是以下底线：

- 尊重项目边界
- 不擅自脑补业务规则
- 不静默吞掉问题
- 保持实现可追溯、可定位、可维护
